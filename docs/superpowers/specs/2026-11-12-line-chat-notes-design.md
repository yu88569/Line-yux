# ระบบโน้ตในห้องแชท LINE

สถานะ: แบบเสนอ รอผู้ใช้ยืนยันก่อนเริ่มเขียนโค้ดผลิตภัณฑ์

## เป้าหมาย

เพิ่มโน้ตของ LINE จริงให้ Line-yux โดยผู้ใช้ขอให้อ่าน สร้าง แก้ไข ลบ และคอมเมนต์ได้ ข้อมูลต้องตรงกับโน้ตที่สมาชิกห้องแชทเห็นใน LINE ไม่ใช่สมุดบันทึกที่เก็บเฉพาะในเครื่อง

## แนวทางที่เลือกเสนอ

เพิ่มหน้าต่าง GTK ภายในแอป และใช้เซสชัน LINE เดิมผ่าน protocol sidecar เช่นเดียวกับระบบอัลบั้ม แนวทางนี้เหมาะกับการจัดการโน้ตครบตามที่ขอ

การเปิดลิงก์ไปแอป LINE ภายนอกไม่ตอบโจทย์การใช้ฟังก์ชันภายใน Line-yux ส่วนโน้ตที่เก็บเฉพาะในเครื่องไม่แชร์กับสมาชิกในห้อง จึงไม่เลือกสองแนวทางนี้

## สิ่งที่ผู้ใช้จะเห็น

- ปุ่ม “โน้ต” บริเวณหัวห้องแชท เปิดหน้าต่างของห้องนั้น
- รายการโน้ตแสดงผู้เขียน เวลา และตัวอย่างเนื้อหา พร้อมรีเฟรชและโหลดรายการต่อ
- กดรายการเพื่ออ่านเนื้อหาเต็มและคอมเมนต์
- ปุ่มสร้างโน้ตและช่องพิมพ์ข้อความหลายบรรทัด
- ปุ่มแก้ไขและลบแสดงเฉพาะโน้ตของผู้ใช้เอง เมื่อตรวจสอบผู้เขียนได้
- ลบต้องมีหน้าต่างยืนยันที่แสดงโน้ตเป้าหมาย
- อ่านคอมเมนต์และเพิ่มคอมเมนต์ข้อความจากหน้ารายละเอียด
- ระหว่างส่งปิดปุ่มส่งซ้ำ เมื่อผิดพลาดเก็บข้อความที่พิมพ์ไว้และแสดงปุ่มลองใหม่
- ข้อความในหน้าจอรองรับภาษาไทยและอังกฤษ

## ขอบเขตเนื้อหา

เริ่มจากสร้างโน้ตและคอมเมนต์แบบข้อความ รวมข้อความภาษาไทยและลิงก์

โน้ตเดิมที่มีภาพ สติกเกอร์ หรือตำแหน่ง ต้องแสดงว่ามีสิ่งแนบอย่างชัดเจน ห้ามทำให้ดูเป็นโน้ตว่าง การแก้ไขต้องรักษาสิ่งแนบเดิมทั้งหมด หากยังรักษาโครงสร้างไม่ได้ ให้ปิดการแก้ไขเฉพาะโน้ตชนิดนั้นและแสดงเหตุผล การเพิ่มสิ่งแนบใหม่ไม่อยู่ในขอบเขตรอบแรก

การแก้ไขหรือลบคอมเมนต์ และการกดไลก์ ไม่อยู่ในขอบเขตรอบแรก ผู้ใช้ขอคอมเมนต์โดยยังไม่ได้ระบุสองความสามารถนี้

## ข้อจำกัดที่พบจากซอร์ส

- SDK ที่โปรเจกต์ล็อกไว้คือ `@evex/linejs@3.2.1` มี `base.timeline` สำหรับอ่าน สร้าง แก้ไข ลบโพสต์ และสร้างคอมเมนต์
- `createPost` ปฏิเสธ home ID ที่ขึ้นต้นด้วย `u` จึงยังรับรองการสร้างโน้ตในห้องส่วนตัว 1 ต่อ 1 ไม่ได้ รอบแรกเสนอให้เปิดความสามารถเต็มในห้องกลุ่มปกติที่ตรวจสอบแล้ว และแจ้งข้อจำกัดในห้องชนิดอื่น
- ห้องหลายคนแบบเก่าบางชนิดไม่มีโน้ตตามคู่มือ LINE และไม่ถือว่าการไม่มีสิทธิ์เป็นรายการว่าง
- API รายการคอมเมนต์และโครงสร้างผลลัพธ์ยังต้องตรวจสอบก่อนสร้างตัวแปลงข้อมูล ห้ามเดารูปแบบแล้วแสดงว่าใช้งานได้
- ยังไม่ได้เรียก Notes API ด้วยบัญชีจริง การมี wrapper ใน SDK เป็นหลักฐานว่ามีทางเชื่อม ไม่ใช่หลักฐานว่าทุกคำสั่งทำงานกับเซสชันปัจจุบันแล้ว

## โครงสร้างสำหรับผู้พัฒนา

ข้อมูลฝั่ง UI ใช้ `Note`, `NotePage`, `NoteComment`, `CommentPage` ที่มี ID ผู้เขียน เนื้อหา เวลา ข้อมูลสิ่งแนบ และ cursor ที่ผ่านการตรวจสอบแล้ว สถานะโหลดใช้ชนิดที่แยก loading, ready, empty, failed และ exhausted ชัดเจน

เพิ่มโมดูลโน้ตฝั่ง TypeScript เพื่อแยกการตรวจอินพุต การเรียก API และแปลงผลลัพธ์ออกจากตัว dispatch หลัก เพิ่มคำสั่ง sidecar สำหรับรายการ รายละเอียด สร้าง แก้ไข ลบ รายการคอมเมนต์ และเพิ่มคอมเมนต์ ส่วน Rust ใช้โมดูลหน้าต่างโน้ตและ Pending responses ตามรูปแบบอัลบั้ม

ทุกคำสั่งผูกกับห้องและ note ID ที่เปิดอยู่ ไม่ใช้ห้องปัจจุบันภายหลังสลับแชท การปิดหน้าต่างทำให้คำตอบที่มาช้าไม่มีผลต่อหน้าต่างอื่น

การสร้างโน้ตและคอมเมนต์ต้องระบุ `sourceType: TALKROOM` และสิทธิ์ของห้องอย่างชัดเจน ห้ามใช้ค่าเริ่มต้น `TIMELINE` หรือ `ALL` โดยไม่ตรวจสอบความหมาย ห้ามใช้ API birthday board ที่เคยถูกเข้าใจผิดว่าเป็นโน้ต

การแก้ไขหรือลบตรวจผู้เขียนอีกครั้งในชั้น protocol และให้เซิร์ฟเวอร์ LINE เป็นผู้ตัดสินสิทธิ์สุดท้าย เมื่อไม่ทราบผู้เขียนให้ปฏิเสธการแก้ไขหรือลบ ห้ามแสดงผลสำเร็จก่อนเซิร์ฟเวอร์ตอบรับ

ไม่ส่งคำสั่งสร้าง แก้ไข ลบ หรือคอมเมนต์ซ้ำอัตโนมัติหลัง timeout เพราะผลครั้งแรกอาจสำเร็จแล้ว ให้รีเฟรชตรวจผลก่อนผู้ใช้ตัดสินใจลองใหม่

## ลำดับการทำงานและการพิสูจน์

1. ยืนยัน API ของโน้ตห้องกลุ่ม รายการคอมเมนต์ รูปแบบข้อมูล cursor และตัวระบุผู้เขียนจากหลักฐานจริงหรือ primary source ก่อนลงมือเชื่อมคำสั่งที่เกี่ยวข้อง
2. เพิ่มตัวแปลงและคำสั่ง protocol พร้อมทดสอบด้วย transport จำลอง ตรวจขอบเขตห้อง สิทธิ์ และการคงสิ่งแนบ
3. เพิ่มหน้าต่าง GTK และปุ่มโน้ต พร้อมทดสอบกดใช้งานจริงโดยใช้ sidecar จำลอง ครอบคลุมการโหลด แก้ไข ลบยืนยัน คอมเมนต์ การสลับแชท การกดซ้ำ และความผิดพลาด
4. ตรวจ build และชุดทดสอบที่เกี่ยวข้อง ตรวจการอ่านบนเซสชันจริงเท่าที่เข้าถึงได้โดยไม่เปลี่ยนข้อมูลในห้อง หากไม่มีทางทดสอบบัญชีจริงให้ระบุส่วนที่ยังไม่ยืนยันอย่างตรงไปตรงมา

ไม่ใช้การทดสอบสร้างโน้ตหรือคอมเมนต์ในห้องจริงเป็นขั้นตอนอัตโนมัติ การเผยแพร่ข้อความจริงเกิดจากผู้ใช้กดใน UI เท่านั้น ไฟล์แก้ไขระบบดาวน์โหลดที่ติดตั้งแล้วต้องคงอยู่ครบ
